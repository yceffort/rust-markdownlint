# musl CLI 성능 개선 계획과 실행 기록

## 목표와 기준

기준 커밋은 `a039aee`다. Thin LTO와 Linux jemalloc이 이미 적용된 배포용 `x86_64-unknown-linux-musl` CLI에서 추가 개선을 검증한다. 출력 내용, 정렬, 종료 코드와 Markdown 규칙 의미는 유지한다.

성능 측정은 기존 4 vCPU GitHub Codespace에서만 수행한다. 로컬에서는 코드 편집과 회귀 테스트를 수행한다. 기존 A/B의 GNU 수치를 이번 개선율 계산에 사용하지 않는다.

## 이번 실행 범위

1. 기본 진단 출력: stderr를 한 번 잠그고 제한된 크기의 버퍼로 출력한다. 진단마다 생성하던 중간 문자열을 줄인다. 포매터 종료 전에 명시적으로 flush하여 프로세스 종료 시 출력이 유실되지 않게 한다.
2. 파서 이벤트 소유권 이동: 사용이 끝난 벡터 전체를 `split_off(0)`으로 꺼내는 경로에서 불필요한 새 할당을 없앤다. 토크나이저 재사용이나 이벤트 인덱스 재설계 없이 적용 가능한 범위부터 실험한다.
3. 중첩 노드와 평탄한 토큰 트리의 통합은 이번 실행에서 재설계하지 않는다. 앞의 두 후보를 검증한 결과와 다음 조사 항목을 이 문서에 기록한다.

## 검증 방법과 채택 기준

- 기준, 출력 변경만, 파서 변경만, 두 변경 조합의 musl 바이너리를 같은 Rust 버전과 Cargo.lock으로 빌드한다. 빌드가 모두 끝난 뒤 측정한다.
- 기존과 같은 fixture 388개, 블로그 445개, fixture 10배 3,880개를 사용하고 파일 내용과 상대 경로 해시를 기록한다. 저장소 설정은 제외하고 `noBanner: true`를 사용한다.
- 각 바이너리의 종료 코드, stdout, stderr를 기준 바이너리와 바이트 단위로 비교한다. 큰 stderr가 파이프로 전달되는 경우도 확인한다.
- 코퍼스별 3회 준비 실행 후 24회 측정한다. 네 바이너리의 24개 순열을 사용해 순서를 균등하게 배치한다. 시간은 blocking wait로 측정하며 출력은 `/dev/null`로 보낸다.
- 모든 개별 샘플, 평균, 표준편차, 중앙값, 실행 순서, 바이너리 및 코퍼스 해시를 JSON으로 보관한다. 같은 라운드의 기준 대비 차이도 함께 확인한다.
- 출력 일치와 회귀 테스트를 통과하고 반복 측정에서 개선이 확인된 변경만 채택한다. 효과가 측정 편차 안에 머무르는 변경은 보류한다. 다른 코퍼스에서 일관된 악화가 있으면 채택하지 않는다.
- 최종 변경은 전체 workspace 테스트, Clippy, 포맷 검사를 수행한다. 출력 버퍼 경계를 넘는 데이터와 flush 오류 전달을 별도로 검증한다.

## 결과

**출력 변경만 채택했다. 파서 후보는 제품 코드에서 제외하고 실험 패치만 보관했다.** 기존 GNU 계측의 출력 약 34ms, 코어 시간 중 파서 본체 약 75%는 후보 선정 근거이며 이번 개선율의 예측값으로 사용하지 않았다.

첫 실행의 블로그 표준편차가 50~75ms여서 같은 바이너리로 확인 측정을 추가했다. 네 바이너리의 24개 순열을 seed 208로 섞었고, 준비 실행 3회 후 각각 24회 측정했다. 두 실행의 시간을 합쳐 하나의 평균으로 만들지 않았다. 아래는 확인 측정의 평균 ± 표본 표준편차(ms)다.

| 코퍼스 | 기준 | 출력만 | 파서만 | 조합 | 출력만 개선율 |
|---|---:|---:|---:|---:|---:|
| fixture 388개 | 84.1 ± 1.9 | 78.3 ± 1.1 | 84.5 ± 3.3 | 78.3 ± 1.2 | 6.9% |
| 블로그 445개 | 434.9 ± 14.2 | 408.5 ± 10.3 | 430.0 ± 6.9 | 403.3 ± 6.8 | 6.1% |
| fixture 3,880개 | 771.5 ± 33.3 | 710.0 ± 20.8 | 762.1 ± 22.9 | 711.6 ± 25.2 | 8.0% |

출력 변경은 같은 라운드의 기준보다 각각 24/24, 23/24, 23/24회 빨랐다. 프로세스 전체 CPU 시간(user + system, 모든 스레드 합계)도 각각 281.8 → 276.7ms, 1474.0 → 1448.8ms, 2565.1 → 2512.1ms로 감소했다. CPU 합계와 벽시계 시간은 더해서 해석하지 않는다.

첫 실행에서도 출력 변경의 평균은 세 코퍼스 모두 개선됐고, 기준보다 빨랐던 라운드는 각각 24/24, 19/24, 24/24회였다. 모든 576개 개별 측정값과 두 실행의 집계는 [원시 JSON](results/musl-output-events-2026-09-07.json)에 보관했다.

파서 단독 변경은 확인 측정에서 기준보다 14/24회씩 빨랐으며, 라운드별 시간 절감의 중앙값은 각각 0.13ms, 1.93ms, 0.77ms에 그쳤다. 첫 실행의 10배 fixture에서는 평균이 오히려 느려졌다. 조합은 블로그에서 출력만 적용한 경우보다 조금 빨랐으나 다른 코퍼스에서는 추가 이득이 뚜렷하지 않았다. 이번 결과로 파서 패치를 채택할 근거는 부족하다.

## 반영 내용과 검증

- 기본 포매터에서 stderr를 한 번 잠그고 64KiB 버퍼로 출력하며, 종료 전에 명시적으로 flush한다. 진단이 없으면 버퍼를 만들지 않는다.
- `Display` 구현으로 줄과 컬럼, 규칙 이름, detail, context를 바로 포매팅해 중간 문자열 할당을 줄였다. 공개 `format_result` 함수의 문자열 반환 인터페이스는 유지했다.
- 네 빌드 모두 세 코퍼스에서 기준과 종료 코드, stdout, stderr가 같았다. 큰 stderr를 파이프로 수집한 결과도 비교했으며 코퍼스 해시는 이전 musl 측정과 일치한다.
- 버퍼 경계를 넘는 Unicode 진단과 마지막 버퍼의 flush, flush 오류 전달을 테스트했다. 최종 출력 변경으로 macOS의 `cargo test --workspace --locked`는 610개 통과, 11개 무시, Clippy `-D warnings`와 fmt 검사는 통과했다. Codespaces의 musl release CLI 라이브러리 단위 테스트도 38개 통과했다.
- 블로그를 별도로 `strace -f -c -e trace=write,writev`로 실행했을 때 `write` 호출은 기준 33,531회에서 출력 변경 32회로 줄었다. 추적 실행은 성능표에 포함하지 않았고 원본 요약을 JSON에 보관했다.
- 실행 중 PR #208이 main에 병합됐다. 병합 커밋 `6801852`와 측정 기준 `a039aee`의 파일 트리가 같음을 확인하고 후속 브랜치에서 변경을 정리했다.

## 재현

같은 4 vCPU x86_64 Codespace에서 실행한다. Rust 1.98.1, musl 타깃과 `musl-tools`가 필요하다. 코퍼스는 [앞선 A/B 재현 절차](remaining-gap-2026-09-07.md#원시-데이터와-재현)로 준비한 세 디렉터리를 사용한다. 준비 작업과 아래 빌드를 마친 후 하네스가 자동으로 측정한다. 기준 커밋 `a039aee`는 Git 이력에 있어야 한다.

```bash
source /home/codespace/.cargo/env
python3 bench/experiments/musl-output-events/run.py \
  --repo /workspaces/rust-markdownlint \
  --work /workspaces/markdownlint-performance/musl-output-events \
  --corpora /workspaces/markdownlint-performance/ab-2026-09-07/corpora
python3 bench/experiments/musl-output-events/confirm.py \
  --work /workspaces/markdownlint-performance/musl-output-events \
  --corpora /workspaces/markdownlint-performance/ab-2026-09-07/corpora
```

`run.py`는 별도 소스 디렉터리에 기준 커밋을 풀고, [patches.json](experiments/musl-output-events/patches.json)에 보관한 두 패치를 각각 적용한다. JSON 문자열 안의 패치 내용은 실제 빌드에 사용한 패치와 SHA-256이 같다. 원래 workspace의 target 디렉터리를 공유하므로 실행 중 다른 Cargo 작업을 병행하지 않는다. 결과는 작업 디렉터리의 `results.json`, `confirmed.json`에 저장한다. 이번 실행은 로컬에서 만든 기준 커밋의 `git archive --format=tar.gz`를 `--archive`로 전달했으며 그 해시도 기록했다.

## 한계와 다음 조사

이번 코퍼스는 진단이 많은 문서 집합이다. 오류가 없는 문서나 LSP의 이득으로 일반화하지 않는다. macOS와 Windows의 성능은 측정하지 않았고, 예전 세션의 rumdl 수치와 이번 결과를 합쳐 새 비교표를 만들지 않는다.

이번에 시도한 벡터 소유권 이동만으로 파서의 큰 비용이 해결되지는 않았다. 다음 파서 작업은 배포용 musl의 함수별 CPU와 할당 프로파일에서 `subtokenize`, 이벤트 재구성, attention 처리의 비중을 나누는 것부터 시작한다. 토크나이저 버퍼 재사용이나 중간 트리 통합은 그 결과에 따라 별도 변경으로 검토한다.
